# Заміри затримки відео: методика й результати

Методика вироблена на HIL 02.10 (KWS-044). Ланцюг розбито на ділянки, кожна міряється окремо так, щоб похибка годинників не входила або була відома:

```
[1] екран/сцена → камера → захоплювач (V399) → кадр у процесі
[2] кодер (x264 / v4l2h264enc) → RTSP-сервер вузла
[3] мережа: вузол → VPS (MediaMTX) → РМ
[4] прийом і декодер РМ (v4l2h264dec) → кадр у процесі
[5] композитор і монітор РМ → скло
```

## Правила (уроки 02.10)

1. **Один годинник — найкраще.** Якщо джерело й приймач на одному хості (спалах на RPi 5, приймання там само), похибки NTP немає. Міжхостові заміри — лише зі зсувом кожного хоста `measure.sh ntp` (відносно VPS) у момент заміру. Годинник ПК (−0,9 с і дрейф) не використовувати.
2. **Аналогова камера не читає машинний код.** Експозиція й напівкадри змішують молодші біти (0 з 80 кадрів). Для ділянки 1 — спалахи або великі цифри, для 2–4 — цифрове джерело з кодом (`codesrc.py`).
3. **Час фіксувати ДО дії.** `t0 = time.time()` перед записом у fb. Перший варіант брав час після запису 4 МБ — мінімуми ~0 мс, тобто нефізичні.
4. **Розфазувати період спалахів.** Період, кратний кадру камери (0,8 с = 20 кадрів при 25 к/с), фіксує фазу: розкид штучно вузький. Додавати випадковий зсув 0–80 мс.
5. **Детектувати стрибок, а не поріг.** Рівні «до» і «після» беруть медіанами вікон, подія — перший кадр, що перетнув половину різниці.
6. **Вибірка ≥ 40 на варіант.** Порівняння 30 проти 60 к/с на 5 кадрах (55 проти 50 мс) виявилось шумом.
7. **Перевіряти реальну частоту захоплення.** Скільки кадрів за 10 с прийшло насправді, а не що замовлено в caps.
8. **Перший кадр — після ключового.** Зі старого GOP декодер віддає сміття: `--skip` ≥ GOP або `--gop` джерела коротший (75).
9. **Wi-Fi-аплінк вузла непридатний для мережевої ділянки.** Зависання ~2 с псують медіану. Міряти по Ethernet, або рахувати лише чисті (між зависаннями) і окремо — частку зависань.
10. **Після заміру повернути стан.** `kambala-nodesim` стартувати, перевірити `is-active`. `pkill -f` — з шаблоном `"codesrc.py serv[e]"`, щоб не вбити власну оболонку.

## Команди (ПК, Git Bash; OpenSSH Windows, через тунель)

```bash
J="-o BatchMode=yes -J root@10.66.0.1"
P5="C:/Windows/System32/OpenSSH/ssh.exe $J gans@10.66.0.10"
# ділянка 1 (V399 напряму; node-sim зупинити, бо тримає пристрій):
$P5 'sudo -n systemctl stop kambala-nodesim; sleep 2; sudo -n python3 /tmp/flash.py seg1 "v4l2src device=/dev/ksim-v399 ! image/jpeg,width=640,height=480,framerate=30/1 ! queue max-size-buffers=1 leaky=downstream ! jpegdec" 40; sudo -n systemctl start kambala-nodesim'
# ділянки 1+2 (через кодер node-sim, локально) і петля через VPS:
$P5 'sudo -n python3 /tmp/flash.py local "rtspsrc location=rtsp://127.0.0.1:8554/video0 protocols=tcp latency=0 ! rtph264depay ! h264parse ! avdec_h264" 40'
$P5 'sudo -n python3 /tmp/flash.py vps "rtspsrc location=rtsp://10.66.0.1:8554/node/sim protocols=tcp latency=0 ! rtph264depay ! h264parse ! avdec_h264" 40'
# ділянки 2–4 цифровим джерелом: README workstation/deploy/latency §9.1
```

## Результати 02.10 (RPi 5 sim, аналогова камера PAL → V399, Wi-Fi-аплінк)

| Ділянка | Як | Результат |
|---|---|---|
| 1: монітор RPi 5 → камера → V399 → jpegdec | `flash.py`, 40×4 варіанти | медіана **67–72 мс**, 45–94; однаково для 640×480@30/@60, 320×240@60, jpegdec/avdec_mjpeg — захоплення реально **25 к/с** за будь-яких caps (аналогова камера PAL) |
| 1+2: + кодер node-sim + RTSP + avdec (локально) | `flash.py` | медіана 82–87 мс → кодер+RTSP+декодер ≈ **+10–15 мс** (разом з оверлеєм і конвеєром node-sim) |
| 2: кодер x264 + RTSP + avdec, цифрове джерело, локально | `codesrc` + `framestamp` | **4–5 мс** (selftest у процесі: 3 мс) |
| 2+3 петля: RPi 5 → VPS → RPi 5 | `codesrc` + `framestamp` | **18–23 мс** чисті; зависання Wi-Fi до 1,9 с |
| 2+3+4: RPi 5 → VPS → РМ, декодер РМ | `codesrc`, `framestamp` на РМ, зсуви NTP +9,4 / +16,0 | **21–26 мс** чисті (`v4l2h264dec` 23–26, `avdec_h264` 21–23); медіани зіпсовані Wi-Fi |
| 5: композитор + монітор РМ | фото | ще не міряно |

Висновок: основна затримка — ділянка 1 (аналогова камера й захоплювач, ≈ 70 мс). Кодер, мережа й декодер разом — ≈ 25 мс на чистому каналі. Налаштування захоплювача й декодера ділянку 1 не скорочують.

## Результати 02.10, частина 2: показ на РМ-1 (RPi 4), V399 на РМ

Камера дивиться на ASUS (HDMI-A-1, екран штурмана), Daewoo (HDMI-A-2, екран пілота) стоїть у правому нижньому куті кадру. Для кожного екрана своя область аналізу (`RMFLASH_ROI`). Кадр спалаху I420 720×576, як у відео вузла. Замір — `rmflash.py` через `rm_kms_flash.sh`, 40 спалахів на варіант.

| Варіант | ASUS | Daewoo |
|---|---|---|
| через labwc (`waylandsink`) | 104 мс (67–132) | 113 мс (84–144) |
| без композитора (`kmssink`, labwc зупинено) | 97 мс (58–157) | 102 мс (70–134) |
| **ціна композитора** | **≈ 7 мс** | **≈ 10 мс** |

- Перші цифри «композитор +25–40 мс» (gray8 320×180, розтягнутий на 1920×1080) хибні. Тоді змішались мій тестовий конвеєр і різниця з RPi 5: RPi 5 пише прямо у framebuffer, без чекання вертикальної синхронізації, і це оптимістична база.
- Навіть без композитора `kmssink` на РМ дає ≈ 97 мс проти ≈ 70 мс у framebuffer RPi 5 на тому самому ASUS. До цих ~27 мс входять подача кадру конвеєром (`fdsrc → rawvideoparse → videoconvert`), чекання вертикальної синхронізації (у середньому ~8 мс, до 16 мс) і різниця RPi 4 / RPi 5. Це межа точності методу, а не ланка ланцюга пілота.
- Розкид усіх варіантів ~±30 мс: камера дає 25 к/с, монітор оновлюється з частотою 60 Гц. Похибка медіани при n = 40 — кілька мс, тож різниця 7–10 мс помітна, але не точна.
- Daewoo повільніший за ASUS на ~5 мс.

Як скоротити показ:

1. **Показ без вертикальної синхронізації:** labwc `allowTearing` разом із протоколом tearing-control. Виграш до кадру (~8 мс у середньому).
2. **Пряма площина без масштабування** і в рідному форматі.
3. **DRM lease виходу пілота** для `kmssink`, без композитора. Виграш ≈ 10 мс.

Головний резерв лишається на ділянці 1: аналогова камера й захоплювач, ≈ 70 мс при 25 к/с.

## Результати 02.10, частина 3: матриця показу (labwc 0.9.8 → 0.20.1, tearing, рідний розмір, kmssink)

Сирі числа — у `protocol.md`. Медіани, мс, n = 40:

| Варіант | Daewoo (пілот) 720×576 | Daewoo рідний 800×480 | ASUS 720×576 |
|---|---|---|---|
| labwc 0.9.8 | 117,8 | 110,0 | 100,6 |
| labwc 0.20.1 | 105,2 | 103,2 | 98,3 |
| labwc 0.20.1 + allowTearing=fullscreenForced | 113,4 | 116,4 | 102,1 |
| kmssink без композитора (≈ DRM lease) | 97,0 | 100,8 | 98,8 |

- **Точність методу ≈ ±5–8 мс на медіану.** Повтор тієї самої конфігурації дав 112,6 і 117,8 мс. Причина в тому, що камера знімає 25 к/с, а це крок 40 мс. Різниці менші за ~8 мс цим методом не розрізнити.
- **labwc 0.20.1** на Daewoo, ймовірно, кращий на ~5–12 мс, на ASUS різниці немає. Версія лишається на РМ-1, і на CM4 стоїть та сама.
- **allowTearing виграшу не дав.** Імовірно, `waylandsink` не вмикає tearing-control, а `fullscreenForced` на це вікно не діє.
- **Рідний розмір кадру** проти масштабованого — без помітної різниці.
- **Без композитора (`kmssink`)** проти labwc 0.20.1: Daewoo −4…−6 мс, ASUS ≈ 0. Це межа виграшу від DRM lease.
- Наступний крок — точніший інструмент: фотодатчик на екрані з частотою опитування ≥ 1 кГц на тому ж хості, замість камери 25 к/с.

## Результати 02.10, частина 4: точне порівняння на екрані пілота (500 замірів на варіант, чергування блоків)

Daewoo, labwc 0.20.1, кадр I420 720×576, 10 блоків по 50, чергування варіантів. Сирі числа — `protocol.md`.

| Варіант | Середнє, мс [95% ДІ] | Медіана | Різниця з labwc [95% ДІ] |
|---|---|---|---|
| labwc | 113,7 [110,8..117,4] | 111,5 | — |
| labwc + allowTearing | 111,2 [109,5..112,8] | 111,9 | −2,6 [−6,6..+1,0] — не відрізняється |
| **без композитора (`kmssink`, ≈ DRM lease)** | **101,1 [99,7..102,5]** | **100,5** | **−12,7 [−16,7..−9,3]** |

- **Ціна композитора labwc на екрані пілота ≈ 11–13 мс.** Це статистично надійно: інтервал далеко від нуля. Один викид 664 мс у блоці 6 зсуває середнє labwc лише на ~1 мс.
- **allowTearing виграшу не дає.**
- Отже, **DRM lease для Flight Display — реальний резерв ≈ 11 мс** на шляху пілота.

## Результати 02.10, частина 5: від скла до скла (головне число) і затримка дисплея

**Від скла до скла на стенді ≈ 158 мс.** Три серії, 497 замірів: 155 / 158 / 160 мс. Схема: РМ-1 блимає на ASUS → аналогова камера → V399 → кодер (`v4l2h264enc`, як у CM4) → VPS (MediaMTX) → РМ-1 → Flight Display → Daewoo. Метод — шаблон сталої яскравості («половинки»). Перші ~330 мс були артефактом АРП камери.

**Дисплей ASUS ≈ 45 мс** проти світлодіода Caps Lock: композитор labwc, подача кадру й панель.

Оцінка розкладу (мс, приблизно): камера + V399 ≈ 55–60 · кодер і RTSP на РМ-1 ≈ 50 · мережа й MediaMTX ≈ 15–25 · декодер і показ на Daewoo ≈ 30–45.

Сирі числа — `protocol.md`.
