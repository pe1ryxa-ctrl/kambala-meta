# KSRV-027 (чернетка ТЗ на погодження Gans) — повернення ізольованого вузла

Запит: основна сесія, HANDOFF `e05f8ba` (HIL KSRV-019 «ізолювати sim → повернути» неможливий без описаної й перевіреної процедури). Чернетка — хмара, 2026-10-01. Після погодження Gans — task-файл у server (`.agents/tasks/KSRV-027.md`), виконавець — за рішенням Gans (L1 SRV / хмара / нічна routine).

## Живі факти (server, гілка `fallback/ksrv-026` = `94d7599`, містить KSRV-024)
- `infra/README.md` §6.4 «Повернення вузла в експлуатацію» **є** (на гілках KSRV-024/026, у main ще ні): нові ключі на RouterOS → новий блок у `/etc/kambala/wg-peers` з `node_id` → `apply.sh` → `POST /nodes/{id}/confirm` (або `/confirm/reset`) з loopback → `GET /nodes/status`.
- Ендпоінта **розблокування** немає. `NodeRegistry.confirm_node` і `reset_confirmation` (`nodes/registry.py:1057`, `:1125`) ставлять `status = "ok"` **незалежно від того, чи вузол `blocked`** — тобто `/confirm` і `/confirm/reset` (`devices/app.py:683`, `:803`, loopback-only) мовчки знімають блокування «червоного вимикача». Блокування й підтвердження відбитків — різні рішення, а зараз це одна дія.
- Список відкликаних ключів ніде не зберігається: повернути старий (скомпрометований) ключ технічно можна — README лише забороняє словами.
- `apply.sh` на VPS падав на AppArmor — виправлено KSRV-026 (VERIFIED, чекає HIL).

## Мета
Повернення ізольованого вузла — одна явна, перевірена й задокументована дія адміністратора, яка не може випадково (через `/confirm`) зняти блокування і не допускає повернення скомпрометованого ключа.

## Обсяг (пропозиція)
1. **Явне розблокування.** `POST /nodes/{id}/unblock` (лише loopback, як `/block`): тіло `{"confirm": true, "reason": "<непорожній>", "fingerprints": {...}}` — знімає `blocked` лише разом зі звіркою актуальних відбитків (як `/confirm`); аудит `unblock` (хто/коли/причина/відбитки). **`/confirm` і `/confirm/reset` для вузла в `blocked` → 409** «вузол заблоковано — використайте /unblock» (змінює поточну поведінку — **рішення Gans**).
2. **Заборона старих ключів.** `isolate_node.sh` (і `revoke.sh`) записують відкликаний публічний ключ у `/etc/kambala/wg-peers.revoked` (дата, вузол, причина). `apply.sh` відмовляє (rc 2, без змін), якщо в `wg-peers` є ключ із цього списку.
3. **Скрипт повернення** `infra/wireguard/restore_node.sh <node_id> --pubkey <новий ключ> --allowed-ips <...> --reason "<...>" --fingerprints-file <json> [--dry-run]` (від root, `--console` або SSH з адреси, що не належить вузлу — як `isolate_node.sh`): перевіряє, що вузол `blocked`; ключ новий (не у `wg-peers.revoked`, не в ядрі в іншого пира); додає блок у `wg-peers` → застосовує через логіку `apply.sh` (файли в `/etc/wireguard/.kambala-stage.*`, KSRV-026) → `POST /nodes/{id}/unblock`; при збою будь-якого кроку — відкат файлу пирів, аудит, rc ≠ 0; dry-run друкує план без змін.
4. **README §6.4** переписати під скрипт; ручна процедура (RouterOS `reset-keys`, звірка відбитків) — як пояснення.
5. **Тести:** стенд 4 пири (як KSRV-019/024): ізолювати `sim` → `restore_node.sh sim` з новим ключем → вузол `ok`, пір у ядрі й файлі, аудит; старий ключ → відмова; `/confirm` на `blocked` → 409; збій `apply`/API → відкат. Мутації.
6. **HIL-скрипт для Gans** (після деплою KSRV-024/026 і цієї задачі): на VPS «ізолювати sim → повернути» з консоллю хостингу напоготові.

## Відкрите для рішення Gans
- (а) `/confirm` і `/confirm/reset` більше не знімають `blocked` (409) — **рекомендую так**; інакше блокування «червоного вимикача» знімається будь-якою звіркою відбитків.
- (б) Чи потрібне друге підтвердження (наприклад, YubiKey `ssh-keygen -Y sign` над запитом розблокування) — зараз захист лише «root на VPS + loopback». Рекомендую відкласти до ролей (Фаза 3).
- (в) Виконавець: хмара (≈ $20–30 з рецензією), нічна routine server, чи L1 SRV.
- Залежності: база — `fallback/ksrv-026` (містить KSRV-024) або main після їх злиття; файли — `infra/wireguard/*`, `nodes/registry.py`, `devices/app.py`, тести; не перетинається з KSRV-025 (релей).
